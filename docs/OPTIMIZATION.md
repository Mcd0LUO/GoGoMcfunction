# 优化级别与循环形态

> 本文回答两个问题：**-O 级别间的差别到底是什么**，以及**为什么语言里要有两种循环**。
> 这是两件相关的事：级别决定编译器能证明什么，语法决定编译器不必证明什么。

---

## 1. -O 级别的语义

借鉴 C++，但有一个关键差别：

```
C++ 的 -O 级别 = 打开了哪些优化
CMCF 的 -O 级别 = 每个优化被允许依赖多强的证明
```

之所以这样定，是因为在 1.12.2 上「优化错误」的代价是**静默的**：命令语法合法、
函数能加载、游戏不报错，只是行为不对。所以一个优化只有在其依赖的分析确实可用时才
被允许启用，而不是作为独立开关自由组合。

| 级别 | 允许的证明强度 | 启用 |
|---|---|---|
| `-O0` | 无需证明（只保证正确性） | 常量池 |
| `-O1` | 结构性、无条件成立 | + CFG 化简、不可达消除、自赋值消除 |
| `-O2`（默认） | 全函数不动点（活跃性） | + 死存储消除、寄存器复用、常量收集 |
| `-O3` | 跨块值分析 | 保留，尚无通过此门槛的优化 |

**级别是单调的**：O1 启用的优化 O2 一定启用。不存在「O3 关掉 O2 的某个优化」。

### 为什么常量池在 O0

这一条值得单独说，因为它是从 bug 里学到的。

字面量 `4` 降级成 `#4 cmcf.c`，它是一个 fake player。如果没人初始化它，
计分板读出来是 **0**。最初我把「生成常量池」归到 O2，结果 `-O1` 的产物里
`x -= #4` 实际减的是 0，程序全错，而且没有任何报错。

**生成常量池是正确性要求，不是优化。** 它现在在 O0 也运行。

### 查看某个级别跳过了什么

```
$ cmcf -O1 -v foo.cmcf
skipped at -O1: dead-store (needs O2: whole-function liveness fixed point; deleting a live write changes behaviour)
skipped at -O1: coalesce-temps (needs O2: interference graph built from liveness; ...)
```

## 2. 两种循环

```
while cond #[budget(N)] { body }    // 前测：先判据，可能一次都不执行
loop  cond #[budget(N)] { body }    // 后测：先执行一次，再看是否继续
```

**两者生成的结构相同**，都是尾测：循环体和判据在同一个块里，回边是自调用。
`while` 只是多一次入口预判，这就是它唯一的区别。

```
while:  T: cond; Branch(cond, B, X)      // 预判一次
        B: body; budget -= 1
           cond; Branch(cond AND budget>=1, B, X)

loop:   B: body; budget -= 1
           cond; Branch(cond AND budget>=1, B, X)
```

### 曾经以为做不到

「把 `while` 的判据移到尾部」这个说法本身就是错的：判据读的值会被循环体改写。

```
while abs(x - prev) >= 1 { prev = x; x = (x + n/x)/2 }
```

判据读 `x` 和 `prev`，循环体会重写它们。把判据挪到尾部，它读的就是更新后的值——
语义完全变了。

但**正确的改写不是移动判据**，而是：

```
while cond { body }  ==  if cond { loop cond { body } }
```

预判保留在入口，因此语义严格相同，而每次迭代都拿到了尾测的好处。
这是 AST 级的等价改写，不需要值编号，也不需要证明任何东西。

手写库里 `sqrt` 那种「尾部判据写成最终值的表达式」是作者手工推出来的——
编译器不需要猜，因为它保留了入口预判。

### 当前生成

```mcfunction
scoreboard players operation @s t1 = @s l4      # d = y - x
scoreboard players operation @s t1 -= @s l3
scoreboard players remove @s l5 1              # budget -= 1
execute @s[score_l5_min=1,score_t1=-1] ~ ~ ~ function t:l/fl$b2   # 继续
execute @s[score_l5=0] ~ ~ ~ function t:l/fl$b3                   # 预算耗尽
execute @s[score_t1_min=0] ~ ~ ~ function t:l/fl$b3               # 判据为假
```

一次迭代：3 条守卫 + 1 次自调用。分开测预算是 1+1（预算两侧）+1+1（判据两侧）
= 4 条守卫 + 2 次调用，多出来的两条不是「一条」。

退出条件是 `NOT(cond AND budget>=1)`。判据有 k 个分支时，补集就有 k 个分支
（`NOT(A OR B) = NOT A AND NOT B`，一个合取式，一条守卫）；再加上预算那一支。
两种写法在这里的规模完全一样，因为叉积两种写法都有。

## 3. 实测效果

对象是 `examples/luo-math-full.cmcf`（原库 309 行 / 17 文件 / 247 条命令）：

```
-O0: files=16  commands=129  objectives=30  consts=9  （无优化，调试用）
-O1: files=15  commands=127  objectives=30  consts=9
-O2: files=15  commands=124  objectives=28  consts=9
-O3: files=15  commands=124  objectives=28  consts=9
```

**静态行数不是重点。** 循环体是热代码，同样的循环写成尾测后每次迭代的控制命令
从 4 条降到 3 条，回边从「调用另一个块」变成自调用。实测 `sqrt(40000)`：

**行数不是主要指标。** `init` 里有 30 条 `scoreboard objectives add` 和 9 条常量初始化，
占 123 条中的 39 条，但它们只在加载时跑一次。真正的每次调用成本要看具体函数：

| 函数 | 命令数 | 说明 |
|---|---|---|
| `lcg_step` | 4 | `(A*s + C) % M` 的最优形式，中间量直接算进 `return` |
| `chance` | 10 | 含一次跨函数调用 |
| `rand` | 13 | 含一次调用 + 一次取模回绕 |
| `sqrt` | 24 | 4 个块（1.12.2 无文件内标签，每个分支是一个文件） |

objective 数只降了 2，因为**名字必须在整个模块内唯一**：`@s` 是整条调用栈共用的
一个寄存器文件，被调函数的 `l0` 就是调用者的 `l0`。跨函数复用名字只有在分配器能证明
两者不会同时存活时才对——而「不在同一个函数里」不构成这种证明。详见第 6 节。

---

| | 静态命令 | 动态命令 | 失败守卫 |
|---|---|---|---|
| 初始 | 131 | 1531 | 21 |
| 合并预算到条件 | 127 | 1022 | 39 |
| 补集化简 | 125 | **896** | **21** |

**−41%，结果不变（`sqrt(40000) = 200`）。**

## 4. 循环：`while` 就是「预判 + 尾测」

`while cond { body }` 与 `if cond { loop cond { body } }` **是同一个程序**，
所以 `lowerWhile` 直接按后者降级，复用已经写好、已经测过的 `lowerLoop`。
没有 CFG 手术，没有值编号，也不需要证明什么——这就是正确的写法。

堆栈里曾留着 `rotateLoops` / `rotatePostTest` 两个函数做真正的旋转，
它们会读错值、把守卫叉积成 4 条、让回边指向错误的块。那些函数已删除：
**AST 级的等价改写不需要它们**，而在任何时候启用它们都会产生能加载、
不报错、但行为错误的程序。

### 预算为什么必须折进条件

直觉上「把预算单独测」只多一条命令，实际是**两条**：预算分支需要两侧各一条
守卫（`budget>=1` 和 `budget<=0`），然后条件还要自己的一对。折进去之后，
条件的补集只付一次。

补集的规模两种写法完全一样——多分支条件本来就产生叉积——所以折进去永远不会更大，
而且总是少一个块、少一次调用。

## 5. `if` / `unless`：单合取分支只要两条命令

1.12.2 的 `function` 有两种带条件的形式（游戏语言文件原文）：

```
commands.function.usage=/function <name> [if <selector>|unless <selector>]
```

`unless <selector>` 是「该选择器匹配不到」——也就是**选择器条件的补集**。
而选择器只能表达**合取**，所以：

- 一侧是单个合取式时，两侧都只要一条命令：`if` 走一侧，`unless` 走另一侧
- 两侧都是析取式时，才需要每个分支一条守卫

这正是区间约定的红利。`d == 0` 两侧都是单合取（`d==0` 与 `d!=0` 恰好互补），
`d != 0` 同理：真值本身是析取（`d<=-1` 或 `d>=1`）需要两条守卫，
但假值是单个合取，所以另一个方向一条就够。

```mcfunction
# d != 0
execute @s[score_t=-1] ~ ~ ~ scoreboard players set @s return 1
execute @s[score_t_min=1] ~ ~ ~ scoreboard players set @s return 1
function t:e/ne$b2 if @s[score_t_min=0,score_t=0]
```

原来无条件走「每条分支一个 `execute`」，三选一的预判要三条命令；现在两条。

**这是纯渲染层改写，语义不变**——`unless @s[c]` 就是「c 不成立」，
而且在**当前执行上下文**里跑，和守卫调用解析到的 `@s` 是同一个实体。

## 6. 加新优化时该做什么

1. 在 `analysis/` 写它需要的分析，单独测试
2. 在 `optimize/` 写 pass，测试**断言 IR 结构**而不是输出字符串
3. 在 `Catalog()` 注册，写清 `Requires`——即**它为什么是正确的**
4. 用真实代码验证：至少跑一遍 `examples/luo-math-full.cmcf`

第 3 步不是形式主义。本文第 1 节的常量池 bug 就发生在「没想清楚这个 pass 依赖什么」上。

## 7. 补集只有一份实现

补集是这个编译器里最容易写错、又最不会报错的东西：**匹配过宽会静默走错分支**。
它曾经有三份独立实现——`lower`、后端、优化器各一份——而其中两份**已经分叉了**：

| | 越界边界 |
|---|---|
| `lower.complements` | 丢弃（正确） |
| `backend.complementCond` | 发出 `score_x_min=2147483648` |
| `optimize.complementCond` | 同后端 |

`x == 2147483647` 的补集是 `x < 2147483647` 一条；那两份会再发一条
`x >= 2147483648`——没有任何分数能等于它，但它照样占一条命令和一行报错。

现在只有 `ir.Negate` / `ir.Simplify` 一份，三处调用点都是薄包装，
并有 9 条测试锁住区间约定。**同一份逻辑抄两遍，它们迟早会不一样。**

### 化简补掉了什么

叉积会重复条件。`|d|>=1 AND budget>=1` 的补集原本出来四条：

```
d >= 0 AND d <= 0          ← 真正的退出点（d == 0）
d >= 0 AND budget <= 0     ← 被下面那条覆盖
budget <= 0 AND d <= 0     ← 被下面那条覆盖
budget <= 0 AND budget <= 0 ← 同一条条件写了两遍
```

`Simplify` 把同一 objective 的重复条件并成区间、丢掉被更弱分支覆盖的分支，
四条变两条。

## 8. 名字为什么不能跨函数复用

这一条曾经写错，代价是三个静默误编译，全都在 `luo/math` 里。

`@s` 上的 objective 是**整条调用栈共用的一个寄存器文件**。被调函数执行时，
调用者暂停但仍然握着它的活跃值。所以：

- 局部变量按函数从 `l0` 编号 → `lcg_next` 的 `l0` 就是 `rand` 的 `l0`，
  `lcg_next` 直接冲掉 `rand` 还在用的 `span`；
- 参数寄存器 `a0..` 会被任何嵌套调用在传递实参时写入，而且必须是**传递**的：
  `lcg_next` 自己没有参数，但它把 1 个实参传给 `lcg_step`，所以它写了 `a0`——
  `rand` 的 `lo` 就是这么丢的；
- `CoalesceTemps` 在每个函数里都从 `t0` 重新染色 → 两个函数共用 `t0`。

规则因此是：**名字在模块内唯一，直到分配器证明共享是安全的**。
临时变量一直遵守这条，局部变量和染色名现在也遵守。

另外两条同源的坑，一并记录：

1. **干涉图必须是对称的。** 只记扫描到的那一个方向，会让着色看不见已经占位的邻居。
   在 `chance` 里三个同时存活的值被染成同一个 objective，`rand <= p` 变成恒真。
2. **干涉必须用真正的不动点。** 原来的 `liveAfterBlock` 只看直接后继，
   漏掉穿过回边或块链的冲突——而漏掉的冲突就是两个活跃值共用一个槽。

**改动处理器的调用约定时，先跑 `TestRandMatchesReference`。** 它把整条链
（嵌套调用、跨调用活跃的参数与局部变量、int32 回绕）与一份独立的 32 位参考实现对照，
四个优化级别都要一致。
